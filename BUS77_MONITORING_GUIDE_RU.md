# Руководство по работе с монитором Bus77

В этом руководстве объясняется формат вывода скрипта `scripts/linux/monitor_can_bus.sh`, включая то, на что обращать внимание при нажатии кнопок или включении/выключении нагрузки.
Оно описывает текущую версию инструмента, а не все возможные реализации устройств Bus77.

[English version](BUS77_MONITORING_GUIDE.md) | [Главное описание (README)](README_RU.md)

---

## 1. Запись контрольной последовательности действий

Скачайте монитор и наблюдайте за интерфейсом в течение 5 минут (300 секунд):

```sh
cd /tmp
wget --no-check-certificate -O monitor_can_bus.sh https://raw.githubusercontent.com/efDaCartoonz/irididiag/main/scripts/linux/monitor_can_bus.sh &&
sh monitor_can_bus.sh --interface can0 --duration 300
```

Скачивание перезаписывает старую копию скрипта. Сначала скрипт запрашивает идентификационные данные устройств; дождитесь сообщения **Live packet exchange** перед началом действий. 300-секундное наблюдение начинается после обнаружения. Во время наблюдения монитор только пассивно слушает шину.
Не запускайте другие диагностики/сканеры одновременно. Используйте флаг `--passive`, чтобы полностью пропустить запросы идентификации (в этом случае названия моделей устройств, как правило, будут недоступны).

1. Оставьте систему в покое на 15–30 секунд, чтобы зафиксировать фоновый трафик шины.
2. Обратите внимание на отображаемое монитором время и выполните одно стандартное безопасное действие: нажмите кнопку, отпустите ее или включите свет штатными органами управления.
3. Подождите 5–10 секунд перед следующим действием. Фиксируйте нажатие и отпускание отдельно: короткие, длинные и повторные нажатия могут генерировать разные события.
4. Повторите то же действие 2–3 раза, затем протестируйте обратное действие (включение/выключение).
5. Дождитесь завершения захвата и сохраните файл, имя которого указано в строке **Log saved:**, вместе с вашими заметками о действиях. Лог сохраняется в виде обычного текста (цвета терминала не сохраняются).

Используйте только штатные органы управления. Эта процедура не требует отключения проводов CAN, изменения терминации/битрейта, снятия питания с устройств или работы с силовой проводкой 220В. Если питание с устройства снимается намеренно, зафиксируйте это отдельно от выключения его выхода: это разные эксперименты.

Пример заметок о действиях (подставьте свое время и наблюдения):

| Время на мониторе | Действие | Физический результат |
| --- | --- | --- |
| 12:34:10 | Кратковременно нажал кнопку 1 в коридоре | Свет включился |
| 12:34:11 | Отпустил кнопку 1 | Свет остался включенным |
| 12:34:20 | Снова нажал кнопку 1 | Свет выключился |

Монитор отображает системные часы сервера в момент декодирования сообщения с точностью до 1 секунды. Это не прецизионная аппаратная метка времени и не измерение задержки. Несколько сообщений могут иметь одинаковое отображаемое время.

## 2. Идентификация устройств

Карточки **BUS DEVICES** содержат идентификационные данные, запрошенные в начале работы:

| Поле | Значение |
| --- | --- |
| Model | Модель устройства, полученная из ответа |
| Device name | Имя устройства, сохраненное в нем; может быть стандартным или повторяющимся |
| HWID | Аппаратный идентификатор для различения отдельных устройств |
| Firmware version | Установленная версия прошивки |
| Firmware profile | Номер профиля/ID прошивки (это идентификатор, а не версия или оценка исправности) |
| LID | Локальный адрес на шине Bus77 |
| CAN device ID | Технический идентификатор отправителя CAN, не является полным HWID |

Для удобства монитор дублирует эти карточки в конце работы. Это снимок начального состояния, а не повторный поиск: наличие карточки не доказывает, что устройство оставалось онлайн на протяжении всей записи. Устройства, подключенные позже, могут отображаться по адресу без названия модели.
В карточки попадают только устройства, вернувшие корректные данные идентификации.

## 3. Чтение отдельного сообщения

Наглядный пример (числа ниже приведены для демонстрации и не являются схемой вашей инсталляции):

```text
12:34:10 can0 TX SERVER/GW(S3:LID 0) -> LID 2 DM-306PS | REQUEST GetChannelValue tid=42 | channel=123
12:34:10 can0 RX LID 2 DM-306PS [464E] -> SERVER/GW(S3:LID 0) | RESPONSE GetChannelValue tid=42 | channel=123 value=42
```

| Часть | Как ее читать |
| --- | --- |
| `can0` | Интерфейс CAN, по которому передается сообщение |
| `TX` / `RX` | Передано (TX) / получено (RX) относительно сервера, а не физической нагрузки |
| `SERVER/GW` | Локальный тракт передачи; сервер может пересылать команду другого клиента |
| `S3:LID 0` | Сегмент 3, локальный адрес 0 (это не номер устройства 768) |
| `LID 2 DM-306PS [464E]` | Локальный адрес, известная модель и шестнадцатеричный ID устройства CAN |
| `->` | Отправитель -> получатель |
| `ALL (broadcast)` | Нет конкретного получателя (широковещательное); не гарантирует, что все его получили или обработали |
| `REQUEST` / `RESPONSE` | Запрос / ответ протокола; не обязательно является прямым действием пользователя |
| `tid=42` | Идентификатор транзакции, помогающий сопоставить ответ с запросом |
| `tid=none` | Опциональный TID опущен; это не обязательно ошибка |
| `channel=123 value=42` | Номер канала и его значение; назначение и единицы измерения не угадываются |

Сопоставляйте транзакцию по интерфейсу, адресам, команде, близкому времени и значению TID, а не только по TID: идентификаторы могут повторяться. Без TID время и направление служат лишь косвенными признаками, особенно при пересечении нескольких похожих запросов.

## 4. Что означают распространенные команды

| Команда | Интерпретация |
| --- | --- |
| `Ping` | Проверка доступности; ответ доказывает связь по протоколу, но не срабатывание нагрузки |
| `Search`, `DeviceInfo` | Запросы поиска и идентификации; обычно диагностический/конфигурационный трафик |
| `SetVariable` | Публикует/устанавливает значение глобальной переменной; может быть событием кнопки, обновлением датчика или автоматизацией |
| `GetVariable` | Запрашивает значение глобальной переменной |
| `SetChannelValue` | Запрашивает изменение значения канала управления; проверяйте последующий ответ и физический результат |
| `GetChannelValue` | Считывает значение канала управления; частые повторы могут быть плановым опросом |
| `SetTagValue`, `GetTagValue` | Записывает/считывает значение тега обратной связи; назначение тега требует проектной документации |
| `GetChannels`, `GetTags` | Запрашивает информацию о каналах/тегах, а не изменение состояния |
| `GetChannelDescription`, `GetTagDescription` | Запрашивает текстовые описания; монитор не преобразует все такие данные в понятные имена |

Монитор декодирует основные типы: логические (Boolean), целые числа (integer), числа с плавающей запятой (float) и строки.
Некоторые другие типы выводятся в hex. Значения `true/false` или `1/0` не всегда означают вкл/выкл: они могут означать фронт сигнала, флаг состояния, аварию или инвертированный вход.

## 5. Как сопоставить трафик с кнопкой или выключателем

Пример широковещательного сообщения:

```text
12:34:10 can0 RX LID 5 FS-BT6-OLED [6789] -> ALL (broadcast) | REQUEST SetVariable tid=none | variable=500 value=true
12:34:11 can0 RX LID 5 FS-BT6-OLED [6789] -> ALL (broadcast) | REQUEST SetVariable tid=none | variable=500 value=false
```

Если эти изменения стабильно повторяются после нажатия и отпускания кнопки в ваших записях, то переменная 500 является **кандидатом** на событие этой кнопки. Само по себе это еще не доказывает, каким именно светильником она управляет. Исполнительное устройство может реагировать напрямую на broadcast, поэтому отдельной команды от сервера к реле может и не быть.

Ищите следующую цепочку доказательств (не обязательно все этапы будут видны в логе):

1. **Вход (Input):** повторяющееся сообщение/изменение значения от кнопочной панели.
2. **Управление (Control):** связанная команда по переменной или каналу управления к актуатору.
3. **Отчет о состоянии (Reported state):** связанный ответ или значение обратной связи (если настроено).
4. **Физический результат (Physical result):** свет/нагрузка реально изменяет состояние, как ожидалось.

Ответ с пометкой `acknowledgement` означает, что декодер увидел ответ без payload; это не подтверждение того, что лампа загорелась. Значение обратной связи само по себе может быть целевой уставкой, а не физическим измерением. Для точного понимания необходима документация на проект/устройства.

Записывайте наблюдения как кандидаты до сверки с проектом:

| Наблюдаемое действие | Источник LID/HWID | Команда и ID | Значения | Степень уверенности |
| --- | --- | --- | --- | --- |
| Нажатие/отпускание кнопки | Заполнить | напр., `SetVariable`, 500 | true/false | Устойчивая корреляция; функция еще не подтверждена проектом |

Не подписывайте числовое значение как температуру, CO2, яркость или название комнаты без соответствующей таблицы привязки и единиц измерения. Скрипт не обучается этим значениям автоматически при нажатии кнопок.

## 6. Что делать при необычном выводе

| Наблюдение | Что это означает (и чего не означает) |
| --- | --- |
| В основном идут запросы/ответы Ping | Фоновая проверка доступности; не подтверждает работу кнопок или приводов |
| Нет новых сообщений после нажатия | Может быть локальной логикой устройства, другим интерфейсом, ненастроенным входом или неподдерживаемым трафиком; не доказывает поломку кнопки |
| Повторяющееся событие после каждого нажатия | Хорошая корреляция; подтвердите привязку в проекте перед назначением функции |
| Запрос без видимого ответа | Проверьте broadcast-сообщения, границы записи и опциональность ответов перед выводом о сбое устройства; инструмент не анализирует таймауты ответов автоматически |
| `ERROR data=...` | Флаг ошибки протокола; числовой код ошибки требует анализа контекста |
| `CRC mismatch` | Ошибка контрольной суммы собранного пакета; содержимое не декодируется. Причиной могут быть как проблемы со связью, так и пропуски кадров при захвате/сборке |
| `unfinished packets` | Запись завершилась с неполными данными; нормальная ситуация на границе интервала наблюдения |
| `MORE (message fragment)` | Часть многопакетной последовательности; инструмент не интерпретирует всю последовательность как одно прикладное значение |
| `UNKNOWN_0x...`, `ENCRYPTED`, неподдерживаемый тип или hex | Ограничение декодера/неподдерживаемый формат, само по себе не означает неисправность устройства |
| `payload hidden` | Намеренное скрытие конфиденциальных данных управления, а не потеря пакета |

Состояние контроллера CAN **ERROR-ACTIVE является нормальным рабочим состоянием**, несмотря на слово ERROR.
Состояния ERROR-WARNING/ERROR-PASSIVE требуют внимания; BUS-OFF означает, что контроллер отключился от шины из-за критического числа ошибок. Отличайте накопленные исторические счетчики от новых ошибок/сбросов за время текущего запуска. Историческое предупреждение само по себе не означает текущую неисправность.

Сводка маршрутов подсчитывает декодированные пакеты Bus77, в то время как счетчики RX/TX считают низкоуровневые кадры CAN. Один пакет может занимать несколько кадров, поэтому эти числа не должны совпадать.
Результат `PASS` означает, что выполненные проверки прошли успешно, а не то, что абсолютно все функции проекта работают; `WARN` требует прочтения указанной причины; `FAIL` означает сбой обязательной проверки, но не обязательно требует замены оборудования.

## 7. Сохранение контекста для анализа

Сохраняйте полный файл лога, версию скрипта, выбранный интерфейс, время действий, физические результаты и таблицы привязки каналов/устройств. Удаляйте конфиденциальные идентификаторы и значения перед отправкой логов третьим лицам. Некоторые чувствительные данные скрываются инструментом автоматически, однако **полное отсутствие конфиденциальных данных в логах не гарантируется**.

Этот скрипт не отправляет управляющих команд и не воспроизводит записанный трафик. Для сбора стандартного лога мониторинга менять настройки сервера или устройств не требуется.

См. также: [инструкции и правила безопасности](README_RU.md#диагностика-canbus77-на-hss-и-proav).
